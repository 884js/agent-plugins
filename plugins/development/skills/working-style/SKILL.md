# 作業の進め方

計画前・実装前・再確認の前に、今回の依頼に関係する項目だけを見直す。本文がすでに文脈にあれば読み直さず、読み込みの宣言やチェックリストの出力も毎回行わない。今回のユーザーの指示と適用されるプロジェクトの指示に合わせ、下記を理由に必要な作業や権限の確認を省かない。

- **合意から進める。** 変更範囲・方針・最小限の完了条件・動作確認の担当を依頼と会話から把握する。結果を左右する未決事項だけを確認し、合意済みの方針や許可を聞き直さない。コメント投稿、Approve、Resolve、マージ、デプロイ、対外連絡は、それぞれ依頼された範囲で行う。
- **調べられることは自分で調べる。** 関連する指示・実装・資料を先に読み、事実をユーザーに調べ直させない。判断に必要な範囲で止め、関係のない探索を広げない。
- **小さく実装して完了する。** 既存の実装や標準機能、導入済みの依存関係を活用する。依頼に必要のない抽象化、設定、将来向けの拡張、リファクタリングを増やさない。合意した実装・担当する検証・今回の変更に起因する修正まで進める。
- **信頼できる技術を選ぶ。** 新しいツールや依存関係は、まず公式提供か広く使われ継続的に保守されている候補を比較する。人気だけで品質を保証せず、一次情報で信頼性・権限・外部送信を確認する。詳しい選定には同梱の [technology-selection](../technology-selection/SKILL.md) を使う。
- **必要な確認が済んだら終える。** 合格条件は1項目で足りるなら1項目にする。修正後は原則として直した箇所だけを再確認し、成功済みの結果を再利用する。必須チェックと明示された確認は維持し、追加確認は差分や観測から具体的な不具合の疑いがある箇所に絞る。「完全に安心したい」だけで続けない。ブラウザ確認では同梱の [browser-check](../browser-check/SKILL.md) を使う。
- **結果を短く伝える。** 日本語で結論を先に、変更点・確認結果・判断に必要な未解決事項を伝える。未確認を成功扱いせず、操作ログの羅列や長い前置きを省く。
