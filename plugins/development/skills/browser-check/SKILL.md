# ブラウザで変更箇所を確認する

確認の速さは、対象を絞り、同じ調査や操作を繰り返さないことで確保する。期待結果の確認を省いたり、未確認の項目を合格にしたりして短縮しない。

## 先に最小限の合格条件を決める

- 依頼、差分、適用されるリポジトリの指示から、依頼された結果を確かめるために必要な条件だけを決める。1項目で足りるなら1項目にし、形式的なチェックリストを膨らませない。指定された確認や必須チェックは維持し、分かっている情報は聞き直さない。
- 文言・見た目の修正なら対象の表示、操作の修正ならその操作から期待結果までを確認する。保存機能の変更なら保存後の表示や再読み込み後の保持など、依頼された挙動を証明できるところまで含める。
- 起こり得る影響を網羅しようとして、周辺機能、全ブラウザ、全画面幅、全エラーケースを追加しない。範囲を広げるのは、差分や観測結果から具体的な不具合の疑いがある場合に限り、その疑いを確かめる最小限の箇所を選ぶ。
- 明示されたQA項目や別スキルの必須手順がある場合は維持する。総合QAへこのスキルを適用して確認範囲を狭めない。

## 必要な操作と観測に絞る

- 指定されたブラウザ・環境・タブを使い、対象が合っていれば既存のログイン状態やタブを再利用する。確認のためだけに新しいツールを導入したり、ブラウザや環境を何度も切り替えたりしない。
- 利用中のブラウザ操作ツールの手順に従う。必須の状態取得、スクリーンショット、操作対象の確認を省かず、観測していない状態を推測して連続操作しない。
- 利用者が見る結果を確認する。文言や操作状態はDOM・アクセシビリティ情報などを使い、見た目や配置の判定には実際の画面画像を使う。APIの成功やCSS値だけで画面表示まで合格にしない。
- ツールが自動で待機する操作には不要な待機を重ねない。待つ必要がある場合は、長い固定待ちではなく、対象要素の表示や処理結果などの具体的な条件を待つ。
- 各操作の後に、同じ目的のDOM取得・スクリーンショット・全件ログ取得を機械的に積み重ねない。必要な観測とツールの必須手順で結果が分かれば次へ進む。コンソールや通信の詳細は、確認項目や不具合の切り分けに必要な範囲を読む。
- スクリーンショットの保存や録画は、依頼された証跡や表示確認に必要なものに絞る。証跡を整えるためだけに、成功した操作を最初からやり直さない。

## 合格したら終え、不具合があれば絞って確認する

- 決めた期待結果と必須チェックを満たしたら終了する。「ほかにも問題があるかもしれない」「もっと安心したい」だけでは追加確認しない。具体的な不具合の兆候がなければ、影響の小さい不確実性を受け入れて完了する。
- 修正後の再確認は、原則として今回直した箇所だけにする。同じ環境・表示条件での成功済みの結果を再利用し、1か所直すたびに合格条件を作り直したり、周辺機能を一通り確認し直したりしない。共通部品の修正でも、全利用箇所の確認を自動で追加しない。
- たとえば保存ボタンの文言だけを直したなら、その文言を確認して終える。保存処理や別画面の確認が成功済みなら、それらまでやり直さない。明示的な再確認の依頼や、別箇所に具体的な不具合の兆候が出た場合だけ、その箇所を追加する。
- 失敗したら観測した事実を残し、その原因を切り分けるための操作だけ追加する。原因や条件を変えずに同じ操作・再読み込み・ログインを繰り返さない。修正が依頼範囲に含まれる場合は、修正後にその失敗箇所を再確認する。
- ログイン、環境不備、再現条件不足などで進めない場合は、どこまで確認できたかと不足情報を返す。待ち続けたり、ブラウザ以外の結果で確認済みに置き換えたりしない。
- 操作は依頼された範囲と権限内で行う。確認のために必要な送信・削除・購入などが未承認なら、その操作を行う前に確認する。

## 結果を短く返す

確認した画面・操作と結果を簡潔に伝え、不具合や未確認事項があれば添える。操作ログを逐一並べたり、依頼されていないQA報告書を作ったりしない。確認していない画面幅・状態・環境まで合格とせず、未実施と失敗を区別する。

## 参考

- [Playwright Best Practices](https://playwright.dev/docs/best-practices): 利用者が見る挙動を確認し、ユーザー向けの要素情報を操作の手がかりにする。
- [Playwright Auto-waiting](https://playwright.dev/docs/actionability): 操作に必要な状態を待ち、自動待機に不要な固定待ちを重ねない。Playwrightの導入を必須にするものではない。
