# ネーミング

名前だけを並べず、何を伝えたいのかに照らして選べる候補を示す。新しい名前の提案、既存候補の比較、既存名の見直しのうち、依頼された作業を行う。

## 目的と制約をつかむ

- 会話、README、仕様、周辺の名前を読み、何の名前か、誰がどこで使うか、対象の役割を短く整理する。分かっていることは聞き直さず、判断を左右する不足だけを確認する。
- 名前の言語、読み方、求める印象、避けたい表現、文字数や文字種の制約を拾う。日本語で相談されても、名前自体を日本語にするとは限らない。
- プロダクト名では意味・印象・覚えやすさ、リポジトリやスキル名では役割の分かりやすさ・探しやすさ・入力しやすさなど、今回重視する基準を先に決める。好みが不明なら仮定を短く示す。
- 既存名が不評なら、長さ、曖昧さ、響き、実態とのずれなど、何が合っていないかを具体化する。単に同義語へ置き換えない。

## 方向を変えて候補を作る

- 役割を直接表す、得られる価値を表す、具体的なものにたとえるなど、対象に合う異なる方向を探る。既存候補の比較だけを求められたら、新案を大量に追加しない。
- プロダクトには印象に残る比喩、操作名には動詞、公開パッケージには説明的な名前など、出会う場面に合わせる。すべてを造語や英語に寄せない。
- 語尾だけを変えた候補、用途を説明できない造語、実態より範囲が広い名前を落とす。`tools`、`helper`、`-ify` なども一律禁止にはせず、この対象で意味が伝わるかを判断する。
- 既存名が最も合う場合は、その理由を示して残す案も認める。

## 使う場面で比較する

有力な候補を、次の観点から今回必要なものに絞って比較する。

| 観点 | 確認すること |
| --- | --- |
| 意味と範囲 | 役割が伝わるか。機能を過大に見せたり、必要以上に狭めたりしないか |
| 覚えやすさ | 読める・言える・聞いて綴れるか。略語や造語の説明が毎回必要にならないか |
| 文脈との一致 | 読者、言語、周辺の名前、ブランドの印象に合うか |
| 実際の表記 | リポジトリのパス、インストール名、名前空間付きの呼び出し、会話の一文にしたとき自然か |
| 区別しやすさ | 既存名との重複や、同じ利用者が使う別製品との混同がないか |

スキル名だけでなく、配布時の `plugin:skill` の形でも読む。形式上使える名前と、分かりやすい名前は分けて評価する。根拠のない点数や平均点で順位を決めず、各候補の強み・弱点と、優先した基準を説明する。

## 必要な重複確認を行う

- まずリポジトリ内や同じマーケットプレイス内の名前を確認する。公開名を選ぶ場合は、用途に応じて公式レジストリ、GitHub、Webなどで既存利用を調べる。ドメインは必要な場合だけ対象にする。
- 外部検索には候補名と公開できる一般的な用途だけを使い、非公開の企画、コード、顧客情報を送らない。ユーザーが外部検索を望まない場合はローカル確認に留める。
- 名前空間が空いていることと、同名の有名製品がないことを区別する。検索結果がないだけで「利用可能」と断定しない。
- 確認した範囲・日付・根拠リンクと未確認事項を示す。ドメイン登録や商標の利用可否は、一般検索だけで保証しない。確認できない候補も、未確認と明示して提示できる。

## 選べる形で返す

通常は方向の異なる3〜5案程度に絞り、名前、読み方が必要なら読み、伝わる意味、良い点、弱点、実際の使用例を簡潔に示す。候補数や出力形式が指定されていれば従う。

最も合う候補を、その対象で重視した基準に結びつけて推す。確認済みの事実と主観的な好みを分け、候補がどれも弱ければその理由と次に変える方向を示す。

名前の提案はファイルの改名や設定変更の許可ではない。改名まで依頼されている場合は、参照元、公開識別子、利用者への互換性を確認して依頼範囲を変更する。合意済みの作業は聞き直さない。
