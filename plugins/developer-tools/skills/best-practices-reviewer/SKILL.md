# Best Practices Reviewer

実装前の方針または変更コードを、必要な範囲だけ調べてレビューする。特定のエージェント製品やコマンドを前提にせず、利用できるツールとプロジェクトの指示に合わせる。

## 進め方

### 1. 対象を定める

- 依頼内容から、方針レビュー、コードレビュー、実装支援のどれに当たるかを特定する。
- ユーザーが指定した範囲、期待する動作、制約を基準にする。範囲指定がなければ、今回の変更差分と判断に必要な周辺コードを対象にする。
- リポジトリ内の探索で解決できることは先に確認し、結果を左右する選択だけを質問する。
- レビューのみの依頼ではコードを変更しない。

### 2. 根拠を集める

- リポジトリルートから対象ディレクトリまでに適用されるエージェント指示、コントリビューションガイド、規約と、その参照先を読む。
- 対象に適用される Lint、フォーマット、型、ビルド、テストの設定と検証用スクリプトを確認する。
- 変更箇所の呼び出し元、共通処理、データの流れを追い、同じ役割の周辺コードとテストを確認する。単一の実装例をプロジェクト全体の慣習と断定しない。

### 3. 評価する

- 明文化された規約と有効な設定を、明文化されていない既存慣習より優先する。明示ルール同士の矛盾を解消できない場合だけ質問する。
- 期待する動作と境界条件を満たし、変更が必要最小限で、既存の共通処理や依存関係を再利用しているか確認する。
- 命名、配置、型、import/export、責務、エラー処理、非同期処理、テストの書き方が周辺実装と整合しているか確認する。
- 入力境界、権限、データ損失、セキュリティ、アクセシビリティなど、変更内容に関係する安全性を省略しない。
- 同じ修正を繰り返している場合は追加の対症療法を止め、再現条件、前提、共通経路から原因を見直す。作業やコンテキストの分割は必要な場合だけ提案する。

### 4. 検証する

- 実装前に、変更リスクに見合う最小の検証方法を決める。複雑または広範な変更では方針と検証方法を共有し、小さく明白な変更では形式的な計画を要求しない。
- 実装を伴う場合は、対象に応じて既存の Lint、フォーマット確認、型チェック、テスト、ビルドを実行する。
- レビューのみの場合は自動修正を行わない。検証できない項目は理由と残るリスクを明記する。

### 5. 報告する

- 根拠のある問題を重要度順に示す。コードへの指摘には対象の `ファイル:行番号`、根拠、影響、最小の修正案を添える。
- 「規約違反」「既存慣習との不一致」「任意の改善提案」を区別し、好みの違いを規約違反として扱わない。
- 問題がなければ、確認範囲と実行した検証を簡潔に伝える。未確認の範囲まで問題なしと断定しない。
- レビュー範囲外の一括整形、リファクタリング、追加機能を持ち込まない。
